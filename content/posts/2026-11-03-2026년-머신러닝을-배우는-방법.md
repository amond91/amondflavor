## 한 줄 요약

ML 엔지니어 Vicki Boykis는 Yacine과의 인터뷰에서, 2026년에도 ML 기초와 Git·SQL·명령줄 같은 소프트웨어 기본기를 직접 익혀야 에이전트가 이끄는 대로 끌려가지 않고 방향을 정할 수 있다고 말한다. 검증된 자료와 Kaggle 재현, 작은 개인 프로젝트, 숙련자의 리뷰를 학습 경로로 권한다.

## 핵심

- 경제학 전공 후 무역 컨설팅에서 Excel로 분석하다가 R·SAS 자동화를 보고 프로그래밍을 배웠고, 데이터 분석→데이터 과학→ML 엔지니어링으로 전체 과정에서 직접 할 수 있는 일을 늘려 왔다. Tumblr 추천, Duo ML 플랫폼, Mozilla.ai LLM을 거쳐 현재 Malachyte에서 전자상거래 검색·추천·실시간 개인화를 개발한다.
- 기초 학습 경로는 2026년에도 크게 달라지지 않는다. 2023년 무렵 만든 'normcore LLM reads'(word2vec, Transformer, SVM, 딥러닝 시스템, 선형대수 등)를 지금 갱신해도 구성은 유지할 만하며, 책을 읽고 nanoGPT를 구현하면 KV 캐시가 해시 맵·딕셔너리·Redis와 닮았다는 식의 패턴을 알아볼 수 있다. LLM은 막힌 개념의 설명과 구체적 예시를 얻는 데 쓰되 학습의 노력까지 넘기지는 말아야 한다.
- 소프트웨어 엔지니어에게는 코드가 실행되는 것과 결과가 올바른 것을 구분하는 것이 핵심이다. 출발점으로 Kaggle 프로젝트(Titanic, iris, 펭귄 종 분류 등)를 두세 개 직접 재현하고, LLM이 생성한 프로젝트보다 검토가 충분히 된 사람의 노트북을 셀 단위로 읽는 편을 선호한다.
- Git, SQL, 명령줄은 에이전트 환경에서도 직접 다룰 줄 알아야 한다. 변경을 hunk 단위로 검토하고 커밋도 직접 하며, SQL 실행과 결과 확인을 많이 위임할수록 데이터와 문제에서 멀어졌다고 말한다. 익숙하지 않은 저장소에서 모델 제안에 계속 동의하고 있다면 멈추고 더 읽어야 할 신호다.
- 에이전트와 일할 때는 화이트보드로 서비스 간 상호작용을 먼저 그리고, 진입점 코드를 직접 쓴 뒤 에이전트에게 계획을 요청하며, 구현 전에 코드를 보여달라고 하고 작은 단위로 확인한다. 버릴 시제품이나 내부 구현이 중요하지 않은 작업은 더 많이 위임해도 된다.
- 새 기술은 훑어보고 2~3개월 뒤에도 논의되는지 확인한 뒤 깊이 본다. RAG는 유행이 식었어도 Perplexity나 검색 결과의 문맥 링크 형태로 쓰이고, 사고 사슬은 모델의 추론 기능에 흡수되었다. 좋은 학습 프로젝트의 조건은 자신이 해결하고 싶은 개인적 문제와 숙련자의 지속적인 외부 리뷰다.
- 로컬 모델(LM Studio, llama.cpp, Gemma 등)은 작은 분류 작업, 외부 API에 보내기 싫은 데이터 처리, 추론 구성 학습에 유용하다. 다만 InfiniBand·분산 GPU 환경은 실제 운영 경험 없이는 배우기 어렵다. 주변 실무자 사이에서는 프로젝트별 일일 토큰 추적과 작업별 모델 라우팅 등 비용 관리가 중요해졌다.

## 자세히

인터뷰의 일관된 주제는 '기초를 배우는 이유는 모든 일을 손으로 하기 위해서가 아니라, 에이전트가 자신을 이끌게 두지 않고 직접 방향을 정하기 위해서'라는 것이다. 에이전트는 주어진 데이터를 세계의 전부처럼 취급해 복잡한 해법을 만들 수 있고, 데이터와 사업 맥락을 연결하는 이해가 있어야 문제 자체를 단순하게 바꿀 수 있다고 한다. LLM이 좋은 소프트웨어의 평균적 형태를 재생산한다면, 효율이나 새로운 아이디어가 필요한 곳에서는 그 틀을 넘어서는 안목이 사람에게 필요하다는 주장도 나온다.

학습 방식에 대해서는 Anthropic의 AI 보조와 코딩 역량 연구를 인용한다. 코드 생성만 맡기기보다 설명과 개념을 질문한 참가자가 새 Python 라이브러리 Trio 과제 직후 평가에서 더 높은 이해도를 보였다. 다만 이는 학습 직후 평가이며 장기 기억 유지까지 확인한 것은 아니다. 또 LLM에 잘못된 자료를 주면 그것을 좋은 자료로 가정하고 문제 있는 부분까지 그럴듯하게 정당화할 수 있다는 점도 지적한다.

ML 인프라의 어려운 문제로는 상태 관리, Kubernetes, 지연 시간, 보안·의존성 관리, 배포 버전 확인이 꼽힌다. 특히 LLM은 사용 사례가 매우 다양해져, 모델을 교체한 뒤 기존 고객의 실제 용도를 계속 만족하는지 확인하기 어렵고 테스트를 많이 해도 일부 사용자는 이전보다 나빠졌다고 느낄 수 있다. 일부 기업 고객이 개인정보·통제권·미세 조정 때문에 공개 모델을 원한다는 이야기는 대화에서 관찰한 사례이며 산업 전체의 변화로 단정하지는 않는다.

## 왜 골랐나

AI 에이전트 개발 관점에서, 에이전트에게 위임할 범위와 사람이 직접 검토할 범위(hunk 리뷰, 직접 커밋, 사전 설계 후 계획 요청)에 대한 구체적인 작업 방식이 참고가 된다. 모델 교체 뒤 회귀 검증과 작업별 모델 라우팅·토큰 비용 추적 이야기도 에이전트 운영과 맞닿는다.
