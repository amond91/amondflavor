## 한 줄 요약

Jev는 ChatGPT 공동 개발자 Diogo Almeida가 세운 TypeSafe AI의 모델로, 글을 쓰지 않고 분류·점수·예/아니오 확률처럼 타입이 정해진 판단만 반환한다. 원문(Clay의 Alex Lindahl)은 GTM 워크플로에서 'Claygent 조사 → Jev 판단 → 통과한 행만 LLM 작성' 순서로 연결해 비용을 줄이는 방법을 안내한다.

## 핵심

- Jev는 입력 텍스트(state)와 판단 기준(questions)을 받아 답을 반환한다. 질문 유형은 Choice(최대 255개 선택지, 선택지별 확률·신뢰도), Score(사용자가 정의한 2~10단계, 단계별 확률·신뢰도), Noul(예/아니오, 0~1 확률)이며, 한 API 요청에서 여러 질문을 독립적·병렬로 처리한다.
- LLM은 토큰을 순차 생성하지만 Jev는 답을 한 번에 산출한다. 학습 방식 RLCD(Reinforcement Learning for Calibrated Decisions)는 확률이 실제 정답률과 맞도록 하는 데 초점을 둔다(예: 0.8이면 약 80% 정답). 모델 계열명 System One은 카너먼의 System 1/2 구분에서 따왔다.
- '193배 빠르고 445배 저렴', '환각이 수학적으로 불가능'이라는 주장에는 단서가 붙는다. 수치는 TypeSafe 자체 테스트 결과이고 실제 개선 폭의 상단에 해당한다. 환각 불가는 선택지 밖의 답을 만들지 않는다는 뜻일 뿐, 선택지 안에서 틀린 답을 고를 수 있고 기준 문구를 문자 그대로 해석한다. 컨텍스트 한도는 64k 토큰이고, 불필요한 정보를 더 넣으면 정확도가 떨어질 수 있다.
- 도구 선택 기준은 다음과 같다. 명확한 규칙이면 수식/조회, 판단이 분류·점수·예/아니오면 Jev, 문장 생성이면 LLM, 웹 검색이나 다단계 조사면 Claygent를 쓴다. 기준 자체가 모호하면 모델 호출 전에 ICP와 분류 기준부터 구체화해야 한다.
- Clay에는 네이티브 연동이 없어(원문 작성 시점) HTTP API 열(POST api.typesafe.ai/v1/systemone, Bearer 키)로 연결한다. state에는 필요한 필드만 짧게 넣고, 'unclear' 선택지를 두며, Score가 정수가 아닌 가중평균(예: 2.6)을 반환하므로 반올림하거나 구간으로 변환한다.
- 신뢰도 기반 라우팅 예시는 0.90 이상이면 자동 시퀀스 등록, 0.70~0.90이면 담당자 검토, 0.70 미만이면 추가 조사 또는 제외이다. 되돌리기 어려운 작업에는 더 엄격한 기준을 쓴다. 50개 행으로 시험하고 그중 20개를 직접 라벨링해 비교하며, 오답이면 선택지별 확률을 확인해 기준의 겹침이나 모호함을 먼저 고친다.
- 비용은 입력 100만 토큰당 $0.042이다. 요청당 약 300토큰이면 행당 약 $0.0000126, 10만 행에 약 $1.26이다. 더 큰 절감은 Jev가 걸러낸 행에서 유료 데이터 보강과 LLM 작성을 실행하지 않는 데서 나온다. 원문에는 Clay 'Use AI' 열과의 비용 비교 및 HTTP 열의 크레딧 과금 여부가 [FILL IN]/[VERIFY]로 비어 있다.

## 자세히

Jev가 겨냥하는 문제는 Clay 같은 GTM 자동화 테이블 작업의 대부분이 글쓰기가 아니라 작은 판단의 반복이라는 점이다. 직함이 구매 담당자인지, 회사가 ICP에 맞는지, 채용 공고가 구매 신호인지, 답장이 '지금은 아님'인지 '관심 없음'인지 같은 판단이다. 이런 판단은 1행과 4만 행에서 같은 방식으로 나와야 하고, 다음 열이 바로 쓸 수 있는 형식이어야 한다. 원문은 LLM이 문자열을 내놓아 파싱해야 하는 것과 달리 Jev는 "choice": "investor", "confidence": 0.91처럼 정리할 것이 없는 출력을 준다고 설명한다.

활용 사례로는 인물 유형 분류(운영 창업자, 투자자, 초기 직원, 창업자 지원 조직), ICP 적합도 점수, 채용 공고·보도자료·실적 발표에서의 구매 신호 탐지, 답장 분류와 전달(신뢰도가 낮으면 사람 검토), 제각각인 산업·부서·기술 스택 이름의 분류 체계 정규화, Claygent 조사 결과가 특정 주장을 뒷받침하는지 검증, 비용 발생 전 필터링이 소개된다. 흔한 실수로는 겹치는 선택지('Enterprise'와 'Large company'), unclear 선택지 부재, 모든 작업에 단일 신뢰도 임계값 적용, 전체 enrichment 결과를 state에 붙여넣기, Jev에 글쓰기를 시키는 것이 꼽힌다.

오류 처리는 429(rate limit)와 529(서비스 과부하)면 Clay 요청 속도를 낮추고 재시도하며, 422는 대개 병합된 필드 안의 따옴표나 줄바꿈 때문에 JSON이 깨진 경우라고 한다. 이 글은 Clay Creator in Residence가 쓴 가이드이고, TypeSafe 콘솔은 작성 시점에 early access라고 밝힌다. 글 말미에는 저자의 인터랙티브 강좌(uare.ai) 홍보와 무관한 OpenAI 관련 소문 한 줄이 붙어 있다.

## 왜 골랐나

AI 에이전트 개발 관점에서 '생성 LLM'과 '보정된 확률을 반환하는 판단 모델'을 분리하고, 신뢰도 임계값으로 자동 처리·사람 검토·추가 조사를 나누는 파이프라인 설계 패턴이 참고할 만하다. 특허·기술 분류처럼 분류 기준이 명확한 반복 판단 작업에도 같은 구조를 적용해 볼 수 있으나, 이는 원문이 다루지 않은 연결이다.
