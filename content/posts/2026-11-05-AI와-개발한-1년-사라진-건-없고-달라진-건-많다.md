## 한 줄 요약

AI 에이전트와 1년여간 혼자 개발한 경험을 바탕으로, 코드 작성보다 에이전트의 진행과 결과를 통제·개선하는 개발 과정(하네스 엔지니어링)을 설계한 사례를 공유하는 시리즈의 첫 편이다. 설계 → 구현 → 검증의 결과가 다시 설계와 규칙의 개선으로 돌아오는 닫힌 피드백 루프가 핵심이다.

## 핵심

- 하네스 엔지니어링을 에이전트 설정과 도구 조합에 한정하지 않고, 코드 생산성이 급증한 조건에서 품질을 유지하도록 개발 과정 전체를 다시 디자인하는 일로 정의한다.
- 설계와 규칙은 구현 컨텍스트 밖에서 검토한다. 구현 맥락을 공유한 리뷰어는 전제와 사각지대도 공유하기 쉬우므로, 고정된 코드 스냅샷을 독립된 세션에서 검토하고, 검토자는 외부 사례와 공식 문서도 확인하며, 별도의 검증자가 지적의 근거를 재확인한다.
- 구현 중 쌓인 규칙 위반 기록을 외부 감사에 활용해 규칙을 신설·개정·폐지하고, 다음 감사에서 반영 여부를 추적한다. 규칙 작성 원칙은 규범과 현황 분리, 예외 목록 대신 판정 기준 작성, 다수의 관행을 근거로 삼지 않기, 위반 코드에서도 규칙이 호출되는지 확인하기다.
- 리뷰는 수렴하도록 설계한다. PR별 지적 장부로 이전 지적의 해결 여부를 먼저 확인하고, 작성자의 해명을 읽기 전에 코드로 판정하며, 수정하지 않은 코드에 대한 새 지적은 심각한 문제로 제한한다.
- 머지 이후에도 코드 생존율과 디렉터리·파일·함수의 복잡도 추이를 관찰한다. 반복 재구현이나 중복의 징후가 보이면 해당 버전의 diff로 내려가 실제 변경을 조사한다.
- 에이전트의 완료 보고 대신 실행 기록과 코드 변경을 확인한다. 판단은 에이전트에 맡기되 계수와 비교는 실행 도구가 담당한다.
- 사람의 일은 코드 작성에서 스펙 정의와 이해 축적으로 이동한다. 대량 코드 생성보다 생성 스펙을 다듬는 데 훨씬 긴 시행착오가 필요했다.

## 자세히

글쓴이는 특정 도구보다 각자의 제품과 조직에 맞는 개발 체계를 만드는 관점을 공유하는 것이 목적이라고 밝힌다. 구조는 크게 세 갈래다. 첫째, 설계·규칙을 구현 컨텍스트 밖에서 검토하는 것. 둘째, 리뷰를 수렴시키고 머지 뒤에도 관찰하는 것. 셋째, 사람의 역할을 스펙과 이해 쪽으로 옮기는 것이다.

사람의 역할 변화와 관련해서는, 설계 검토·리뷰·감사에서 패턴과 기술 지식을 추출하고 서로 다른 해법을 비교함으로써 위임으로 생기는 이해 격차를 메운다고 설명한다. 글은 사람이 코드를 거의 직접 작성하지 않는다면 코드 구조도 기계가 유지보수하기 좋은 방향으로 바뀌어야 하는가라는 질문을 남기며 마무리한다.

## 왜 골랐나

AI 에이전트 개발에 직접 맞닿는다. 독립 세션 리뷰, 규칙 위반 기록 기반 감사, 코드 생존율·복잡도 관찰 같은 항목은 에이전트 개발 워크플로 설계에 참고할 수 있다. 사람의 역할이 코드 작성에서 스펙 정의로 이동한다는 논지는 기술경영 관점에서도 볼 만하다.
