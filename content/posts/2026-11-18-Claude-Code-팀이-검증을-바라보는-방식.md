## 한 줄 요약

Claude Code 팀은 코드의 약 90%를 Claude가 작성·리뷰하는 환경에서, 모든 diff를 읽는 대신 에이전트가 실행 결과 같은 증거로 작업을 입증하는 검증 루프를 구축했다. 핵심은 E2E·속성 기반·차등 테스트, 앱의 실제 실행(verify 스킬), 그리고 검증기 자체를 변경으로부터 보호하고 실제 장애로 평가하는 것이다.

## 핵심

- 검증 루프가 없으면 사람이 모든 결과를 확인해야 해 Claude를 한두 개만 돌리게 되지만, 있으면 수십~수백 개를 병렬 운용할 수 있다. 구조화된 파일 생성 내부 테스트에서 별도 평가기가 평가 기준표로 검사하자 표준 프롬프트 루프보다 작업 성공률이 최대 10포인트 올랐고, 가장 어려운 문제에서 개선 폭이 가장 컸다.
- 투자할 테스트 세 가지: E2E(실제 사용자 흐름, 속이기 어렵고 완료 기준이 명확), 속성 기반(왕복 인코딩·불변 조건·멱등성·동등성을 fast-check, Hypothesis, proptest로 수천 입력 생성), 차등 테스트(기존 시스템을 정답 기준으로 삼는 대규모 마이그레이션용). 불안정한 테스트는 에이전트가 코드 수정 대신 재실행하게 만들고, 느린 테스트는 문제 위치 파악을 어렵게 한다.
- 테스트보다 중요한 것은 앱을 처음부터 끝까지 실제로 실행하는 것이다. 웹은 Claude Chrome 확장, 모바일은 iOS/Android MCP, 데스크톱은 컴퓨터 사용, 백엔드는 로컬 실행을 쓰고, 실행 방법을 .claude/skills/ 아래 verify 스킬로 정리한다. Anthropic은 거의 모든 변경을 이 E2E 스모크 테스트 방식으로 검사한다.
- 사람의 주의는 검사 실패를 기준으로 배분한다. Claude가 세 차례 수정해도 실패하면 멈추고 사람을 호출한다. 코드 소유자가 검사를 직접 작성하며, 39개 항목의 신뢰성 체크리스트(실행 조건·검사 내용·근거 장애/PR 연결) 중 diff와 조건이 맞는 3~10개만 검사한다.
- 검사 규칙은 검사 대상 변경이 수정할 수 없게 분리한다. Code Review는 기준/기본 브랜치의 REVIEW.md를 읽고 PR이 바꾼 파일은 쓰지 않는다. 리뷰는 특정 커밋에 고정되며, 오래된 커밋의 통과는 현재 변경을 보증하지 못한다. PR 전에는 테스트·빌드·린터 같은 저비용 검사를 먼저 돌린다.
- 새 게이트는 off/observe/enforce 모드로 도입한다. observe는 차단하지 않고 차단했을 상황만 기록해 오탐을 검토하며, 한 세션에서 두 번 차단되면 다음 커밋은 허용해 에이전트가 막히지 않게 한다. 각 커밋에는 검증 방식을 기록하고 미검증이면 none을 남긴다.
- 검증기 자체를 되돌린 변경·병합 전 거부된 변경·정상 변경(크기를 맞춘 표본)으로 평가한다. 재현율은 최초 발견·검증 후·최종 리뷰 단계별로 따로 재고, 수정 중요도 태그(Important, Nit, Pre-existing)를 쓴다. 놓친 버그는 규칙 후보로 만든다(최소 2개 PR에서 발생, 에이전트 3개가 반증 시도 후 사람이 승인). 불안정한 테스트는 skip·sleep·재시도 없이 근본 원인을 찾고, 못 찾으면 삭제하고 이유를 기록한다.

## 자세히

이 글(Addy Osmani 작성, 2026-11-16 게재)의 중심 주장은 검증 계층을 하나의 시스템처럼 관리해야 한다는 것이다. 검사 대상 변경으로부터 보호하고, 실제로 중요했던 버그로 평가하며, 놓친 사례는 기록해 재발을 막고, 쌓인 규칙은 정기적으로 정리한다. 테스트 모음, 검증 단계, .md 파일은 방치하면 계속 커지기 때문이다.

검증 결과를 다음 작업에 반영해야 루프가 닫힌다. 예를 들어 사용자 데이터가 로그에 포함되는지 검사하는 테스트에서 에이전트가 반복 실패하면, 훅이나 CLAUDE.md의 명시적 규칙을 추가해 재발을 (대부분) 막을 수 있다. 리뷰어도 기본 리뷰어 위에 더 비싼 두 번째 리뷰어를 쌓기보다 REVIEW.md로 기본 리뷰어를 조정하고, 이전 회차의 맥락과 과거 실패를 이어받게 하는 편이 비용이 적고 더 많은 문제를 찾는다고 한다.

강한 피드백 루프가 갖춰지면 사람의 역할은 모든 diff를 읽는 일에서 완료 기준을 정의하고 증거를 검토하는 일로 옮겨가며, 이것이 여러 Claude를 동시에 운영할 수 있는 조건이라고 글은 결론짓는다.

## 왜 골랐나

AI 에이전트 개발 관점에서 verify 스킬, 훅, CLAUDE.md/REVIEW.md 규칙, 3회 실패 시 사람 호출, observe 모드 게이트 같은 패턴을 에이전트 파이프라인 설계에 바로 참고할 수 있다. 기술경영 관점에서는 사람의 역할이 리뷰어에서 완료 기준 정의자로 옮겨가는 조직·프로세스 변화 사례로도 읽힌다.
