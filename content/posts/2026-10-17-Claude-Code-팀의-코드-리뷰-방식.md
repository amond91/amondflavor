## 한 줄 요약

Claude가 자체 코드의 약 90%를 작성하는 Claude Code 팀은 코드 읽기 대부분을 기계(AI 리뷰·보안 검사·CI)에 맡기고, 사람은 위험 판단과 결과 책임에 집중하도록 리뷰 체계를 바꿨다. 6월~9월 병합 PR은 2배 이상 늘었고 되돌려진 비율은 40% 넘게 줄었다.

## 핵심

- 리뷰의 판단 기준을 「사람이 코드를 읽었는가」에서 「무엇이 잘못될 수 있고 어떤 검사가 잡아야 하는가」로 바꿨다. 리뷰는 마지막 승인 관문이 아니라 작성 중 맞춤법 검사처럼 계속 실행되며, 대부분의 변경은 사람이 보기 전에 Claude 리뷰와 수정을 최소 한 차례 거친다. 배경으로 Anthropic 모노레포의 일일 반영 변경 수는 5월 약 2,500건에서 9월 3만 건 이상으로 늘었다.
- 목표는 대부분의 PR을 작성자를 포함한 사람 최대 1명의 관여로 병합하되 되돌리기·사고를 늘리지 않는 것이다. PR당 사람 승인 수(중앙값, 95백분위수), 사람 댓글 수, 사람 대기 시간을 추적하며, 되돌리기·사고 비율은 안전 기준(guardrail)으로 쓴다.
- 여러 방어 계층을 둔다. PR 전 자체 검증(테스트·빌드·스크린샷, 새 맥락의 하위 에이전트 리뷰) → 모든 PR에 Claude 리뷰(여러 에이전트가 병렬로 버그를 찾고 다른 에이전트 집단이 투표로 검증) → 병합을 막는 보안 리뷰와 CI → 위험도별 사람 승인 → 병합 대기열·기능 플래그·단계적 배포 → 빠른 롤백.
- 사람 승인은 작성자가 아니라 변경 자체의 위험도로 정한다. 저위험(문서, 플래그 뒤의 추가 변경 등)은 자동 검사만으로, 중위험은 1명, 고위험은 2명이 필요하다. 완화 경로는 신뢰 목록의 작성자에게만 적용되고, 에이전트 승인은 사람 승인을 대체하지 못하며, 승인은 특정 커밋에만 유효하다. 에이전트에 지시한 사람은 필수 리뷰어 1명으로 계산된다.
- 리뷰어는 실제 사고를 평가 데이터(eval)로 삼아 매일 평가하고, 댓글에 대한 사람의 반응(수정/오류/의도된 동작/무관)으로 잡음을 측정한다. 한 CLI PR이 하룻밤에 50회 넘게 리뷰·수정을 반복했고, 반복 지적 코드의 약 59%는 첫 리뷰 때부터 있던 코드였다. 그래서 3회 라운드 상한, 이후 새 변경분만 재리뷰, 버그 유형 단위 지적, 중복 지적 금지를 도입했다.
- 사람은 무엇을 만들지(방향·범위), 결제·자동 업데이트·CI 같은 위험 코드, 패턴이 되는 아키텍처, 검증 증거를 판단하고 배포 결과에 책임을 진다. 코드베이스 이해 공유는 공식 절차 없이 Claude에게 해당 부분의 설명 자료를 요청하는 방식에 의존한다.
- 한계로, 잘못된 병합의 발견은 여전히 작성자·당직자·대시보드에 의존하며 지표 악화 시 승인 요건을 자동 강화하는 안전장치(circuit breaker)는 아직 없다. 팀은 사람 없는 병합 범위를 넓히기 전에 이를 원한다.

## 자세히

공개 제품인 Code Review for Claude Code는 Team·Enterprise 플랜에서 정식 제공되며 발견 사항을 게시할 뿐 승인하지는 않는다(승인은 사람의 결정). 내부 저장소는 소유자가 저위험 변경을 자동 검사만으로 병합하도록 정할 수 있고 그 경계는 계속 바뀌고 있다. 연구 프리뷰 출시 당시 실질적 리뷰 댓글을 받는 내부 PR 비율이 16%에서 54%로 늘었고, 1,000줄 넘는 PR 대부분에서 문제가 발견된다. 관리자는 저장소별로 Quick/Standard/Deep을 고른다.

리뷰 품질 관리 측면에서, 발견 사항은 투표를 통과해야 게시되고 스타일·진단·정리성 지적은 걸러지며(내부 PR에서 A/B 테스트 후 채택), Important/Nit/Pre-existing으로 구분된다. 모든 발견에는 수정하거나 사유를 적어 스레드를 닫아야 하고, 미해결 버그·보안 항목이 있으면 병합할 수 없다. CLAUDE.md(스택·관례·목표)와 코드 소유자가 쓰는 REVIEW.md(영역별 중요한 실패 유형, 사소한 지적 제한, 파일·줄 번호 증거 요구)로 리뷰어를 조정한다.

팀 도입 순서로는 짧은 CLAUDE.md와 훅 → /code-review·/security-review → REVIEW.md → 필수 CI와 PR 템플릿(Testing, Risk, How to revert) → 한 저장소에서 시범 후 확대 → 승인 정책은 엄격하게 시작해 근거에 따라 완화 → 사고·되돌리기를 평가 데이터화하는 순서를 제시한다. 소유권 규범은 「land it, own it」이며 작은 변경, 되돌리기 가능성, 영향 범위에 비례한 검증, 비난 없는 사고 회고가 이를 뒷받침한다.

## 왜 골랐나

AI 에이전트 개발 관점에서, 검증 수단 제공·새 맥락의 하위 에이전트 리뷰·투표 기반 검증·라운드 상한 같은 에이전트 간 협업·수렴 설계 패턴이 직접 참고가 된다. 기술경영·기술정책 관점에서는 위험 등급별 승인, 책임 소재(지시한 사람이 책임), 사고를 eval로 전환하는 거버넌스 사례로 읽을 수 있다.
