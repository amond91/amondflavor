## 한 줄 요약

Patrick Debois(QCon London 발표, InfoQ)는 AI 에이전트에 주는 컨텍스트를 코드처럼 다뤄 생성 → 평가 → 배포 → 관찰의 수명주기(Context Development Life Cycle)를 적용하자고 주장한다. 컨텍스트에 테스트·버전 패키지·보안 검사·출처 추적·소유권을 갖추면 조직이 신뢰하고 재사용하는 지식이 되고, 배포 여부와 자율성 수준은 위험에 따라 사람이 정해야 한다고 한다.

## 핵심

- 컨텍스트는 코드 생성의 입력이자 제품 기능 자체가 될 수 있다. 온보딩의 수많은 예외 상황을 코드로 구현하는 대신 자연어 스킬을 에이전트에 전달한 사례가 나온다. DevOps가 개발 방식을 운영에 적용했듯 SDLC를 컨텍스트 관리에 적용하자는 것이 핵심이다.
- 생성: 사람이 Claude Code에 매번 지침을 입력하는 수동 방식은 확장이 어렵다. AGENTS.md(표준화 진행 중), Context7·Ref(의존성 기준 문서 제공), MCP 커넥터(Slack 등), 명세(Kiro, SpecKit) 같은 것을 준비해 두고, 사람은 컨텍스트 큐레이터가 된다.
- 평가: 린팅·구조 검증 → LLM-as-a-judge로 작성 품질 검토 → 기능 평가 → 자체 코드베이스의 종단 간 테스트 순으로 단계를 올린다. 컨텍스트 유무, 이전·새 버전을 Docker 컨테이너의 코딩 에이전트로 비교할 수 있다. 에이전트가 잘못 수행한 작업은 회귀 테스트로 남긴다.
- 평가 결과는 비결정적이고 일부 테스트가 개선되면 다른 테스트가 깨질 수 있다(두더지 잡기). 같은 테스트를 가령 다섯 번 돌려 판단하고, 평가의 98%가 통과했을 때 출시할지는 위험 수용의 결정이라 제품 책임자가 정하게 된다. 오류 예산처럼 반드시 통과할 평가와 변동을 허용할 평가를 나눈다. 공급업체의 기본 지표만으로 검증을 끝내서는 안 된다.
- 배포·보안: Slack 복사나 Git 서브모듈 대신 npm처럼 패키지 관리자와 레지스트리로 버전을 지정해 배포한다. 레지스트리만으로 신뢰가 보장되지는 않아 문서·테스트·유지보수 상태를 확인해야 한다. 스킬에 코드가 들어갈 수 있으므로 악성 스킬 검사(Snyk 컨텍스트 스캐너 등)와 AI Bill of Materials식 출처 추적이 필요하다.
- 관찰: 실패 로그를 보고 에이전트가 지침을 다시 쓰는 자기 개선 루프(Hugging Face, Devin), 코드 리뷰·Slack 피드백, Hud의 운영 중 사건 코드 수집이 컨텍스트 개선의 입력이 된다. 에이전트가 읽는 CLAUDE.md까지 검사하는 컨텍스트 방화벽 개념 증명도 소개된다.
- 자율성은 목표가 아니라 위험에 맞춰 고른다. 실패해서는 안 되는 작업은 사람이 깊이 개입하고, 위험이 낮고 가드레일이 갖춰졌으면 자율성을 더 허용한다. 공유 컨텍스트에는 명확한 소유권과 PR·승인 절차가 필요하고, 모델이 바뀌면 기존 컨텍스트가 어긋나는 컨텍스트 드리프트를 관리해야 한다. 사람마다 다른 버전의 컨텍스트를 쓰는 문제는 아직 미해결이다.
- 결론으로 중요한 것은 Markdown 파일의 양이 아니라 구체적이고 유효한 조직 지식이며, 코딩 에이전트가 엔진이라면 컨텍스트는 연료라고 한다. 기업의 차별점은 코드 자체보다 사업을 이해하는 올바른 컨텍스트에 있을 수 있다.

## 자세히

발표는 컨텍스트 수명주기를 생성·평가·배포·관찰 네 단계로 나누고, 마지막에 보너스로 컨텍스트 플라이휠(팀의 경험을 검증된 컨텍스트로 축적·공유)을 다룬다. 발표자는 에이전트가 컨텍스트 창에 무엇을 넣을지 정하는 컨텍스트 엔지니어링과 구분해, 조직 전체가 준비·관리하는 컨텍스트 산출물에 초점을 둔다고 밝힌다.

평가 단계가 가장 비중이 크다. SWE-bench 같은 벤치마크는 모델 개발자용이지만 같은 방식을 컨텍스트 평가에 쓸 수 있다고 본다. 린팅은 스킬 YAML 메타데이터의 필수 항목·문법·설명 길이 제한을 확인한다. 테스트가 있어야 모델이 이미 아는 정보 제거나 충돌 지침 탐지 같은 체계적 최적화가 가능하고, 새 에이전트를 설치했을 때 기존 컨텍스트가 왜 작동하지 않는지도 재검증할 수 있다.

플라이휠 부분에서는 개발자의 역할이 코드 작성에서 운영, QA 설계, 제품 결정, 데이터 관리로 넓어진다고 본다. 성숙도는 수동 생성 → 지속 저장·배포 → 학습·적응 → 관찰 결과의 선제적 반영으로 설명하며, 도구와 조직 관행을 따로 평가해야 한다고 한다. 컨텍스트 카오스 엔지니어링, 다운로드 수 대 실제 효과 측정, A/B 테스트, 컨텍스트용 GitHub·Kubernetes에 해당하는 플랫폼은 아직 탐색 과제로 남는다. 질의응답에서는 컨텍스트 언어 선택이 모델의 학습 데이터에 영향받는다는 점과, 은행 같은 환경의 자동 배포는 테스트·가드레일·위험 수용 수준에 달려 있다는 점을 다룬다.

참고로 GeekNews 요약에는 컨텍스트 방화벽 개념 증명, 샌드박스 내 의도치 않은 행동 관찰, 다크 팩토리 접근 등이 담겨 있으나, 원문(InfoQ 트랜스크립트)은 Distribute 단계 도입부에서 잘려 있어 이후 내용은 GeekNews 요약에만 근거한다.

## 왜 골랐나

amond 의 AI 에이전트 개발 관심사와 직접 맞닿는다. CLAUDE.md·스킬 같은 컨텍스트를 버전·테스트·소유권을 갖춘 산출물로 관리하는 방식과, 컨텍스트 변경을 평가하는 회귀 테스트·반복 실행·오류 예산 개념은 에이전트 개발 워크플로에 바로 참고할 수 있다.
