## 한 줄 요약

LLM이 확장 코드 작성 비용을 낮추고 현대적 샌드박스가 배포·보안 비용을 낮추면서, 안정적인 코어 위에 사용자가 직접 만든 확장을 얹는 '웹 확장형 소프트웨어'의 기회가 생겼다는 주장이다. 핵심은 광범위한 API 권한 대신 좁은 권한 객체(object-capability)를 넘기는 설계이며, 저자(Cloudflare 재직)는 Dynamic Workers를 유력한 실행 기반으로 제시한다.

## 핵심

- 대부분의 웹 소프트웨어는 다수 사용자가 원하는 기능에 집중해 롱테일 수요를 못 채우고, 기능을 다 넣으면 UI 복잡성 때문에 나머지 사용자에게 제품이 더 나빠질 수 있음. 사용자가 확장을 만들고 공유하는 방식이 대안으로 제시됨.
- 기존 플러그인 모델(AI 에이전트, IDE, 게임 모드, Blender, CAD)은 진입 장벽이 높은 로컬 도구에 치우쳐 있음. Pi는 안정적 코어와 훅을 제공하고 요청만으로 TypeScript 확장을 만들어 재로드·공유하는 'LLM 네이티브 소프트웨어' 사례로 소개됨. 다만 샌드박스를 따로 구성하지 않으면 확장은 Pi와 같은 권한으로 실행됨.
- 적용 영역으로 사내 데이터 플랫폼(토큰 유출 없는 배포 환경, 플랫폼 팀의 데이터 접근·규정 준수 담당), 고객 지원 플랫폼(1차 조사 에이전트 훅, 버튼 추가), 관측 가능성 도구(맞춤 시각화, 수집 시 변환, 경보 시 스크립트·에이전트 실행)를 듦.
- Salesforce는 2007년부터 Apex와 멀티테넌트 플랫폼으로 고객별 코드를 앱 이벤트·트랜잭션 안에서 실행해 온 대규모 선례임. 당시엔 컴파일러, 런타임, 디버거 등을 모두 자체 구축해야 했지만 지금은 선택지가 많음.
- 실행 기반의 요건은 ① 저렴한 실행 비용(유휴 시 약 0달러, 실행당 1센트보다 훨씬 작게) ② 빠른 콜드 스타트(핵심 경로면 이상적으로 한 자릿수 ms) ③ CPU·메모리·네트워크·로그 등 자원 제한 ④ 장애·보안 격리(Spectre 포함).
- 프록시+불투명 토큰 방식은 세밀한 권한 통제가 어렵기 때문에, 승인된 이메일 한 통만 가져오는 함수 같은 좁은 참조를 넘기는 객체 권한 모델이 더 낫다고 봄. 기본 I/O를 제거하면 인증 정보가 노출되지 않고 유출 경로도 없음. TypeScript 권한 정의는 OpenAPI JSON보다 LLM이 다루기 쉽고 토큰도 적게 씀.
- 실행 기술 선택지는 인터프리터(Lua, QuickJS), V8 isolates, MicroVM(Firecracker 등), WASM+WASI이며 상호 배타적이지 않음. Dynamic Workers는 OpenTelemetry 트레이싱, 사용자별 SQLite·R2, Dynamic Workflows, 호스팅 LLM(Workers AI) 등 주변 기능을 함께 제공한다고 함.

## 자세히

저자는 Obsidian을 예로 들어, 설치한 모든 플러그인을 신뢰해야 하는 모델은 위험 부담이 낮은 노트 앱에는 맞지만 고객 기록·금융 거래·개인 메시지를 다루는 소프트웨어에는 적용하기 어렵다고 설명한다. 서버에서 임의 코드를 돌리려면 무한 루프, 키·데이터 유출, 서비스 거부, 암호화폐 채굴 악용 등을 함께 막아야 한다.

플랫폼으로서의 부담도 인정한다. 고객에게 노출한 API는 사전 설계와 장기 지원이 필요하며, LLM이 지원 부담을 줄일지는 확실하지 않다고 한다. 확장 작성은 LLM이 쉽게 해도 소수가 대부분의 확장을 만드는 참여 불균형이 남을 수 있다고도 짚는다. 그럼에도 사용자가 예상치 못한 활용을 만들어내는 플랫폼의 가치는 감수할 만하다는 입장이다.

저자는 Cloudflare 재직자임을 글 서두에서 밝혔고, Dynamic Workers가 '프로덕션 준비가 된 확장형 웹 앱 프레임워크에 가장 가까운 선택지'라는 평가는 그 입장에서 나온 것이다. 편집 가능한 스크레이퍼 데모도 소개되며, 예제는 arXiv 초록 페이지에서 논문 PDF를 읽어 liteparse WASM으로 Markdown으로 바꾸는 것까지 포함한다. 참고 자료로 Kenton Varda의 글과 발표, Cloudflare OS, Ink and Switch의 Malleable Software, Andy Matuschak의 글이 언급된다.

## 왜 골랐나

AI 에이전트 개발 관점에서 에이전트가 생성한 신뢰할 수 없는 코드를 격리 실행하고 권한을 좁은 capability로 위임하는 설계 패턴이 직접 맞닿는다. 또한 플랫폼이 코어를 유지하고 사용자 확장이 롱테일 수요를 흡수하는 구조는 기술경영·플랫폼 전략 관점에서도 참고할 만하다.
