## 한 줄 요약

2026년 10~11월 Anthropic은 사내 모노레포의 Git을 자체 VCS인 Scion으로 교체했고, OpenAI는 Git 명령은 유지한 채 서버 백엔드를 Pando로 재설계했다. 에이전트로 늘어난 푸시·체크아웃·병합 부하에 대해 각 팀이 클라이언트/프로토콜, 서버/저장소, 협업 흐름 중 어느 층까지 바꿨는지를 비교한 글이다.

## 핵심

- Anthropic 사내 모노레포의 일일 병합은 2026년 5월 약 2,500건에서 9월 3만 건 이상으로 약 12배 늘었고, CI 체크아웃은 하루 약 2,500만 회(초당 약 290회)였다.
- OpenAI Pando는 서버/저장소 층만 바꿨다. 서로 다른 브랜치의 푸시를 독립적으로 처리하고 팩파일을 재사용·지역 캐시로 제공하므로, 개발자는 기존처럼 git clone/git push를 쓴다. GitHub(팩 데이터와 브랜치 참조 분리, 단일 저장소 초당 7,200회 푸시), Cursor Continuity(S3 변경 로그, 디스크는 캐시), Entire(지역 미러), GitLab(백엔드 재설계와 파일/이력 조회 인터페이스)도 Git 명령을 유지하는 방향이다.
- Anthropic Scion은 클라이언트와 프로토콜까지 교체했다. 온라인 작업 환경을 전제로 필요한 데이터만 서버에서 받고 커밋·리베이스·병합도 서버에서 처리하며, 코드 리뷰·검색·권한 관리도 함께 구축했다. 일반 Git 저장소로 내보내거나 미러링하는 방법은 발표 글에서 확인되지 않는다고 한다. Anthropic은 대부분의 저장소에는 Git 설계가 여전히 적합하다고 설명한다.
- 푸시 속도와 main 반영 속도는 별개다. Pando 설계를 독립 구현한 오픈소스 Aspen의 자체 실험에서 브랜치별 푸시는 5분간 초당 567회였지만 main에 순차 반영하면 초당 약 4회였다(CI 미포함). Aspen은 여러 PR을 각각 별도 커밋으로 남기면서 main을 한 번만 갱신해 이 비용을 줄인다.
- 병합 가능과 병합 결과의 정상 동작은 다르다. 서로 다른 파일을 고친 두 변경은 Git 충돌 없이 합쳐져도 함께 동작하지 않을 수 있어, GitHub 병합 큐처럼 합친 상태에서 필수 검사를 돌리는 방식이 필요하다. GitLab은 소스 관리 다음 병목으로 CI·보안 검토·배포를 짚는다.
- 리뷰 기록도 바뀌고 있다. Zed Delta는 동료를 에이전트 작업 스레드에 초대해 코드와 대화를 함께 리뷰하며, 대화·편집 기록은 Git 커밋과 별도로 DeltaDB에 저장된다. Entire CLI 체크포인트는 코드 브랜치와 별도의 Git 참조를 쓰므로, main만 옮기면 세션 기록은 따라오지 않는다.

## 자세히

글은 'Git을 쓴다'는 일을 세 층으로 나눈다. 첫째는 클라이언트와 프로토콜(커밋을 만들고 clone/push로 주고받는 방식), 둘째는 서버와 저장소(코드 보관, 작업 환경에 전달, 브랜치 갱신 처리), 셋째는 협업 흐름(리뷰, CI 검증, main 병합)이다. 요약 표에 따르면 Git 명령을 유지한 사례가 대부분이다. OpenAI Pando, GitHub, Cursor Continuity, Entire, GitLab, Aspen, Zed Delta가 여기에 속한다. 교체한 곳은 Anthropic Scion뿐이다.

에이전트가 늘면 부하는 저장소에만 머물지 않는다. 클라우드에서 작업마다 새 샌드박스를 띄우면 코드를 매번 받아야 하고, 푸시 뒤에는 CI가 같은 커밋을 여러 환경에서 다시 가져간다. GitHub의 4월 가용성 업데이트에 따르면 PR 하나가 Actions, 브랜치 보호, 검색, 알림 같은 기능도 함께 움직인다. 저자는 병합 건수 대비 체크아웃 횟수의 비율이 병합 한 건당 체크아웃 횟수를 뜻하는 것은 아니라고 단서를 단다.

저자는 결론에서 몇 년 뒤에도 개발자는 같은 git push를 입력할지 모르지만, 그 앞에서 에이전트가 코드를 가져오는 방식과 그 뒤에서 팀이 변경을 검토·병합하는 방식은 지금과 꽤 달라져 있을 수 있다고 본다. 어느 방식이 일상 도구에 먼저 들어올지는 아직 열린 질문으로 남긴다.

## 왜 골랐나

AI 에이전트 개발 관점에서 에이전트 병렬 작업이 저장소·CI·병합·리뷰 기록에 어떤 부하와 설계 선택을 만드는지 정리한 사례 비교로 참고할 만하다. 기술경영·기술정책 관점에서는 같은 병목에 서로 다른 층의 해법이 나오는 것을 볼 수 있다.
