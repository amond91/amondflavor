## 한 줄 요약

한 개발자가 ChatGPT를 검색 대용으로 쓰던 단계에서 에이전트에 작업을 맡기는 방식으로 옮겨 왔고, Opus 4.5/6 이후 병합 PR 기준 생산성이 약 3배가 됐다. 최근에는 코드 검토보다 QA와 결과 제약 조건을 먼저 생각하며, 사람이 상황을 이해하기 위한 대시보드와 도구를 함께 만들고 있다.

## 핵심

- 초기에는 ChatGPT를 더 나은 Google처럼 쓰고 Ruby 테스트 코드를 복사/붙여넣기했다. Cursor 탭 자동 완성은 이미 작성한 패턴을 이어주는 정도로만 썼다.
- 임시로 맡은 Python 컴퓨터 비전 프로젝트에서 검색과 코드 생성을 결합해 API와 도메인을 배우며 만들었다. 환각은 ChatGPT가 아는 것과 모르는 것의 경계를 알리는 신호로 받아들였다.
- Opus 4.5/6 이후 세밀한 지시와 개입 시간이 줄어, 수개월간 병합한 PR 기준 생산성이 소폭 향상에서 약 3배로 뛰었다. 대신 PR 검토가 새 병목이 됐다.
- 검토 부담은 표준 라이브러리·컴포넌트·패턴을 따르게 해 줄이고, 회사 고유 비즈니스 로직, 고객 데이터, DB 변경·암호화처럼 되돌리기 어려운 부분에 집중한다.
- Opus 5 시기에는 비용과 장황함 때문에 잠시 ChatGPT로 옮겼다. Opus 5.5 이후에는 계획을 '어떤 QA를 할지'와 '되돌리는 비용이 커지기 전까지 앱을 얼마나 진행할지'를 정하는 출발점으로 쓴다.
- 이미지 처리 시간을 150ms 대신 실수로 15ms로 입력했는데 모델이 해냈고, 그 일로 가능한 범위를 재평가하게 됐다. Electron 노트 앱의 iPhone 이전을 맡겼더니 몇 시간 뒤 기본 작동 앱이 설치돼 QA를 요청해 왔고, 월 20달러 구독의 5시간 한도 중 40%를 썼다.
- 여러 프로젝트의 활동 피드, 번다운 차트, 성능 모니터링 대시보드를 만들고 하위 에이전트와 감독 에이전트 구조로 일을 나눈다. 다른 모델이 설계의 빈틈을 공격해 보게 하는 방안도 탐색한다.

## 자세히

글쓴이의 변화는 단계별로 이어진다. 처음에는 검색 도구로 쓰다가 코드 생성(복사/붙여넣기), 탭 자동 완성, 에이전트 프롬프트 순으로 옮겨 갔다. 에이전트 프롬프트가 주된 작업 방식이 된 뒤에도 코드베이스 전체를 머릿속에 두고 모든 줄을 검토했다고 한다.

Opus 4.5/6 이후에는 생산성이 오른 만큼 검토가 병목이 됐다. 글쓴이는 정해진 틀을 따르는 변경은 피해 범위가 제한적이고 리팩터링하기 쉽다고 보고, 사람의 주의를 아키텍처, 마이그레이션 계획, 핵심 비즈니스 로직, 데이터와 접근 보호에 모은다.

Opus 5.5 이후에는 아키텍처 결정을 되돌릴 수 있다고 보고, UI가 불확실하면 여러 안을, 비슷한 아이디어가 셋이면 셋 모두 만들게 한다. 글쓴이는 코드가 빠르게 바뀌는 상황에서 이해를 유지하려고 새 지표와 대시보드를 만든다고 하고, 모델과 사람이 함께 쓰는 도구를 구상한다. 결론으로 예전 방식을 빨리 놓을수록 실행 능력이 커지는 느낌이라고 하면서, 예전 방식에서 그리운 것도 그렇지 않은 것도 많다고 썼다.

생산성 3배는 글쓴이 개인이 수개월간 병합한 PR로 측정한 수치이며, 일반화된 연구 결과가 아니라 개인 경험담이다.

## 왜 골랐나

AI 에이전트 개발 관점에서 계획을 QA 기준과 제약 조건 중심으로 바꾸는 접근, 하위 에이전트와 감독 에이전트 구조, 에이전트 상태·이력 추적용 대시보드 사례가 참고가 된다. 기술경영 관점에서는 AI 도입 후 병목이 구현에서 검토로, 다시 검증과 제약 설계로 옮겨 가는 과정을 보여주는 현장 사례로 읽을 수 있다.
