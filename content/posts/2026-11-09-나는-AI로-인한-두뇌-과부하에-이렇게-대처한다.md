## 한 줄 요약

Claude Code·Codex로 작업을 병렬로 늘리다 보면 맥락 과부하가 생기는데, 저자는 Git 안의 Markdown 티켓을 우선순위 큐로 삼고 사람의 판단이 필요한 항목만 'owner inbox'로 모아 한 번에 하나씩 처리·닫는 방식으로 대응한다. 여전히 피곤하지만 산만하거나 길을 잃은 느낌은 줄었다고 한다.

## 핵심

- 문제 진단: 응답을 기다리며 작업을 늘리면 추가 질문·후속 작업이 새 탭으로 이어져 20개 스레드를 오가게 되고, 결국 시작점과 목표를 놓친다. 저자는 이를 순서(sequencing)와 맥락(context)의 두 문제로 봤다.
- 큐는 Git에 둔다. 티켓은 관련 코드 옆의 Markdown 파일이고 보드 상태는 커밋된 스냅샷이라, 세션이 죽어도 큐가 남고 중요한 정보를 대화창이나 머릿속에 두지 않는다.
- 에이전트는 주기적으로 보드를 처리한다. 새 티켓 조사, 사람이 안전하다고 태그한 작업 구현, 테스트·브라우저 확인, 배포된 항목 검증을 맡는다. 민감한 코드는 브랜치에서 구현하고 먼저 승인을 요청하며, 프로덕션 배포는 하지 않는다.
- 에이전트가 할 수 없는 '결정'은 owner inbox에 모인다. 스크립트가 전체 보드를 읽어 변경 검토, 질문 응답, 상충 관계(tradeoff) 판단 항목을 우선순위 목록으로 만든다.
- 읽기 화면은 Claude artifact다. 매 주기 Git에서 다시 생성되는 전체 보드 페이지와 티켓별 검토 페이지로, 링크 하나로 무엇을 왜 만들었는지 보고 판단한다. 판단은 Git의 해당 카드에 기록되며 페이지는 뷰어일 뿐 기록의 기준은 Git이다.
- 핵심 습관은 한 번에 티켓 하나: 맥락을 불러와 결정하거나 조치를 요청하고 큐에 돌려놓아 닫는다. 이렇게 맥락도 함께 닫혀 다음 항목에 집중할 수 있다.
- 남은 과제는 도구 개선이다. 티켓 맥락 파악을 20분이 아니라 1분으로 줄이는 것, 사람만 내릴 수 있는 결정을 기다리며 막힌 티켓이 끝없이 반복되지 않게 하는 것이다.

## 자세히

저자(sergeykuhne.com 블로그)는 휴식, 입력 전 생각하기, 범위 제한 같은 흔한 조언과 별개로, 작업 방식 자체를 우선순위 큐처럼 재구성하는 개인 실험을 소개한다. 원문 표현으로 '두뇌 RAM'에 맥락을 쌓아 두는 것이 탈진의 원인이라는 관점이다.

역할 분담은 명확하다. 에이전트는 조사·구현·검증을, 사람은 판단과 프로덕션 배포를 맡는다. 사람의 개입 지점을 owner inbox 하나로 모으고 우선순위순으로 정렬해, 여러 대화창에 흩어진 판단 요청을 단일 지점에서 처리하게 한다.

저자는 이 방식이 AI 도구 활용 생산성에서 '큰 진전'이라고 느끼지만, 이것은 개인 경험이며 정량적 검증은 원문에 없다. 스스로도 '살아 있는 유기체'처럼 계속 개선 중이라고 말한다.

## 왜 골랐나

AI 에이전트 개발 관심사와 맞닿는다. 상태를 Git에 두는 방식, 에이전트가 할 일과 사람의 승인·결정을 분리하는 human-in-the-loop 설계, 막힌 티켓의 무한 반복 방지 문제가 에이전트 워크플로 설계에 참고가 된다.
