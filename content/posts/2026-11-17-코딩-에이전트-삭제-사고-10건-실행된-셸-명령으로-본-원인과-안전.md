## 한 줄 요약

올해 9~11월 공개된 코딩 에이전트(Claude Code, Codex, Antigravity, opencode) 삭제 사고 10건을 실제 실행된 셸 명령 기준으로 분석한 글이다. 대부분 좁은 대상을 지우려던 명령이 셸 해석·경로 계산·링크 때문에 루트나 상위 폴더를 가리키게 된 경우였고, 사례별 안전한 명령 형태와 대책의 한계를 함께 정리했다.

## 핵심

- 가장 많은 유형은 명령이 셸을 두 번 거치는 경우다. `wsl -- bash -lc '... $R ...'` 에서는 WSL 바깥 셸이 $R 을 빈 값으로 펼쳐 `rsync --delete` 가 `/` 를 대상으로 실행됐고(claude-code#109735), `wsl --exec` 에서는 재현되지 않았다. PowerShell 에서 `cmd /c "rmdir /s /q \"...\""` 처럼 역슬래시로 따옴표를 감싸면 cmd 가 `rmdir /s /q \` 를 받아 드라이브 루트가 삭제됐다(Antigravity, codex#43343).
- 경로 계산 결과가 루트였던 경우도 있다. Git Bash 의 `cygpath -u 'C:\'` 는 `/c/` 를 돌려줘 약 600GB 가 지워졌고(비어 있지 않아 `${VAR:?}` 로 못 막음), opencode 에서는 읽기 전용 자동 변수 `$home` 대입 실패 후 `Split-Path $home` 이 `C:\Users` 를 돌려줬다. 두 사례 모두 `2>/dev/null`, `-ErrorAction SilentlyContinue` 로 오류가 가려져 있었다.
- 명령 범위가 생각보다 넓은 사례: `xargs -n1 dirname` 이 Application Support 의 공백에서 경로를 나눠 macOS ~/Library 가 삭제됐고, 무시된 폴더 안 경로를 지정한 `git clean -fdX` 는 상위 폴더 전체를 지웠으며, Git for Windows 2.52 에서 `git worktree remove --force` 는 정션이 가리키는 폴더의 파일을 지웠다(--force 없이는 git 이 거부). macOS BSD `pkill` 은 `--signal 0` 을 패턴으로 읽어 다른 Claude Code 세션 등 약 66개 프로세스를 종료시켰다.
- 반복된 패턴: 대부분 본 작업 전후의 정리 단계였고, 오류를 숨기는 옵션이 피해를 키웠으며, 10건 중 7건이 Windows 였다. 작업을 멈춘 뒤에도 삭제가 몇 분 더 이어진 사례가 두 건이고, #109735 의 첫 피해 보고("영향 없음")는 틀린 것으로 드러났다.
- 안전한 형태: `"${VAR:?}/고정이름"`, 계산 경로는 출력 후 루트·홈이면 중단, `-print0 | xargs -0` 또는 `find -exec`, `Remove-Item -LiteralPath`, `$ErrorActionPreference='Stop'`, 링크 먼저 해제, `--force` 없는 `git worktree remove`, `git clean -n` 선확인, 존재 확인은 `pgrep` 후 PID 로 `kill`.
- 대책의 한계: 확인 창은 계산 전의 식($(cygpath ...))만 보여주고, Claude Code 샌드박스는 Windows 직접 실행 시 적용되지 않으며, 실행 전 훅(dcg 등)은 스크립트 파일 안 명령이나 실행 시점 값을 못 본다. 지시 파일(CLAUDE.md)에 적은 금지 문장도 #109627 처럼 어겨질 수 있어, 습관·샌드박스·저장소 밖 백업·훅을 겹쳐 써야 한다고 결론짓는다.

## 자세히

글의 핵심 주장은 "에이전트가 rm -rf 로 넓게 지웠다"가 아니라, 의도는 좁았으나 셸 계층(PowerShell, cmd, Git Bash, WSL)을 오가며 명령이 다시 해석되면서 대상이 바뀌었다는 것이다. 재현 가능한 원인은 macOS 와 Windows 11(Windows PowerShell 5.1, Git for Windows 2.52, WSL2)에서 echo 와 시험용 폴더로 직접 확인했다고 한다. 재현하지 못한 부분(예: 정션 사례의 원인은 에이전트의 설명일 뿐 독립 확인되지 않았고, #107274 는 정확한 명령이 공개되지 않음)은 글 안에서 구분해 적었다.

대책 비교에서 글쓴이는 단일 장치로는 충분하지 않다고 본다. opencode 관리자는 권한 규칙이 명령 문자열에만 맞춰지므로 실행 시점에 계산되는 경로나 스크립트 파일 안의 삭제는 잡지 못한다고 답했고, Claude Code 체크포인트도 Bash 명령으로만 바뀐 파일은 되돌리지 않는다. 호스트 드라이브가 /mnt/d 로 쓰기 가능하게 마운트된 WSL 은 격리 범위 밖에 있지 않다는 점도 지적한다.

필자는 실행 전 훅인 claude-bulkhead 를 직접 관리하고 있고 사례 중 여러 건이 그 규칙의 출발점이었다고 밝혔다. 즉 훅 평가에는 이해관계가 있는 글이다.

## 왜 골랐나

AI 에이전트 개발 관점에서 직접 맞닿는다. 에이전트에 셸 도구를 줄 때 권한 확인·샌드박스·훅·백업을 어떻게 겹칠지, 에이전트 지시문만으로는 부족하다는 점이 설계 참고가 된다.
