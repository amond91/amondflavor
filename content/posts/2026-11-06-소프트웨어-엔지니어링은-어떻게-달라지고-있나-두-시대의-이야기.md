## 한 줄 요약

Neil Kakkar(Bloomberg→PostHog→Tano)의 월간 PR 수는 AI 도입 이전 PostHog 시절보다 Tano에서 약 11배(약 19개→207개) 늘었다. 그는 이 증가를 AI 코딩 에이전트뿐 아니라 담당자 단독 책임, 선택적 사람 리뷰, 제품 의사결정 방식의 변화가 함께 만든 결과로 설명하며, 병목은 사라지지 않고 사람의 주의력과 맥락 관리로 옮겨갔다고 말한다.

## 핵심

- The Pragmatic Engineer 에세이 공모(125편 접수)의 우승작(상금 1만 달러)이다. 저자는 Bloomberg 약 3년, PostHog 약 4년, Tano 8개월(첫 엔지니어, 현재 약 10명)을 경험했다. 개인 PR 생산량은 Bloomberg→PostHog에서 2.4배, PostHog→Tano에서 11배 늘었다. 저자 스스로 경력·회사 규모·문화가 달라 AI만의 효과를 분리한 비교는 아니라고 밝힌다.
- Tano는 한 사람이 기능 전체(설계·프런트엔드·백엔드)를 맡고, 코드베이스에 익숙해진 뒤(저자는 약 3주, 최대 8주)에는 사람 리뷰가 선택이 된다. 모든 PR에 Claude Code GitHub Actions 기반 리뷰 에이전트가 CI로 돌고, 위험한 변경에는 더 깊이 보는 에이전트를 따로 돌린다. PR 병합 시간 중앙값은 1시간 미만이다.
- 빠른 배포의 대가로 실제 장애가 났다. 에이전트가 모든 통화에 100을 곱해 바레인 디나르(1디나르=1,000 fulūs)에서 오류가 났고(1시간 내 수정), 약 25GB·600만 행 posts 테이블에 쓰기를 막는 마이그레이션을 걸어 수집 파이프라인이 멈췄으며, 에이전트 아키텍처 이전 중에는 동일 작업에 두 번 지급되는 문제도 생겼다. 새 실패 유형은 리뷰 에이전트 검사 항목(대형 테이블 목록, 차단형 마이그레이션 금지 등)에 추가한다. PR 되돌리기 비율은 이전의 6분의 1이지만, 되돌리기보다 forward fix를 선호하는 영향이 크다고 한다.
- 새 병목은 협업·승인 대기, 다음에 만들 것의 결정, 사람의 주의력이다. 3~5개 작업을 병렬로 돌리면 하루 끝이 이전보다 더 지치고, 쉽게 시작할 수 있어 생기는 스래싱(thrashing)도 늘었다. 저자는 동시 작업 수를 제한하고 중요한 일부터 처리하며, 퇴근할 때 노트북을 회사에 두어 로컬 에이전트가 1~2시간 더 돌게 한다.
- 공유 맥락이 줄고 버스 팩터가 1에 가까워지는 문제가 있다. Tano는 하루 약 30개 PR을 병합하고, 숙련된 동료의 코드는 거의 리뷰하지 않는다. 제품 영역별 AGENTS.md로 이를 완화하겠다는 것은 아직 가설이다.
- 아키텍처가 되돌리기 어려운 선택에서 프로덕션 정보를 보며 고치는 선택으로 바뀌었다고 본다. 저자의 경력상 대형 마이그레이션은 5건(PostHog person-on-events는 전사 1년 작업, Tano는 에이전트 아키텍처 이전 등 3건을 각각 수 주 안에 완료)이다.
- PR 증가는 사업 성과가 아니다. 업계 평균 PR 증가는 약 2배로 소개되며, 제품 시장 적합성·매출·단위 경제성을 함께 봐야 한다고 한다. 또 AI는 조직 프로세스가 함께 바뀔 때만 효과가 크다고 하며, 이미 잘 돌아가는 사업은 변경에 더 신중해야 한다고 한다.

## 자세히

저자는 PostHog 수치를 AI 도입 이전의 우수한 엔지니어링 기준선으로 쓴다. 그가 PostHog에서 AI 도입 이전 시절로 돌아가 혼자 현재 AI를 쓴다면 생산성 향상은 1~2배에 그칠 것으로 본다. 사람의 PR 승인이 필수여서 작성 속도만 빨라지고 승인 대기열이 길어지기 때문이다. 즉 11배는 도구뿐 아니라 리뷰 선택화, 단독 소유, PM 부재(엔지니어가 PM 역할 겸임), 월요일 로드맵 회의 같은 운영 방식과 결합된 수치다.

운영 측면에서 Tano는 각자 20x Claude Max 구독 1개를 쓰며, 저자의 사용량은 API 요금으로 환산하면 월 8,000달러 이상이다. 아직 클라우드 에이전트는 쓰지 않는데, 기본 Claude 에이전트로는 로컬과 같은 실행 환경을 만들기 어렵고 자체 통합 환경 구축은 현재 규모에 맞지 않는다고 판단한다. 또 AI 스타트업에서 디자인이 경시되는 경향과 AI 디자인끼리 서로 비슷해지는 문제도 지적한다.

제공된 원문은 PRs 통계 차트 설명과 "Context-maxxing" 절 중간에서 끊겨 있어, 이후 부분(조직 문화·결론 등)은 GeekNews 요약 페이지에 의존했다.

## 왜 골랐나

AI 에이전트 개발 관점에서 리뷰 에이전트에 실패 유형을 규칙으로 누적하는 방식, 영속 메모리·관측성을 갖춘 에이전트 아키텍처 이전, 동일 작업 이중 지급 같은 에이전트 가드레일 사례가 직접 참고가 된다. 기술경영 관점에서는 도구 도입만으로는 처리량이 늘지 않고 조직 프로세스가 병목이 된다는 논점과, 생산량(PR 수)과 사업 성과를 구분해야 한다는 점이 연구 소재가 될 수 있다. 다만 이는 저자 1인의 자기보고 사례다.
