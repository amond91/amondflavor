## 한 줄 요약

저자는 LLM 제공업체의 사용량·분석 화면만으로는 엔지니어링 판단에 필요한 시계열 토큰 사용 통계를 얻기 어렵다고 보고, 자체 LLM 프록시를 직접 운영해 가시성과 통제권을 확보하라고 주장한다. 특정 프록시 제품은 추천하지 않고, 통제 가능한 환경에서 직접 운영하며 필요에 맞게 수정하라고 권한다.

## 핵심

- 제공업체가 보여주는 작업 진행 표시나 Analytics 화면은 엔지니어를 위한 시계열 토큰 사용 통계가 아니어서 의사결정에 쓰기 어렵다고 비판한다. OTel 내보내기 옵션이 있어도 자체 프록시를 운영할 이유는 따로 있다고 한다.
- 자체 프록시를 운영해야 하는 이유로 다섯 가지를 든다. (1) 여러 제공업체와 모델을 직접 통제하는 단일 엔드포인트로 연결, (2) 어떤 키가 어떤 모델을 어떤 클라이언트로 언제 호출했고 상태가 어땠는지 로그로 기록, (3) 가상 API 키로 주 API 키가 작업·에이전트·하네스마다 흩어지는 것을 방지, (4) 인프라를 직접 통제, (5) 전체 설정을 다시 하지 않고 모델과 제공업체를 빠르게 교체.
- 특정 프록시 제품을 추천하지 않고, 자신이 통제하는 곳에서 직접 운영하라고 권한다. 선택한 프록시는 필요에 맞게 수정할 수 있으며, 저자는 더 나은 가시성, 맞춤형 MCP 서버 엔드포인트, 추가 기능을 위해 개조했다고 한다.
- 저자는 코딩 세션 중 발생한 캐시 미스의 원인을 수동으로 20초 안에 특정할 수 있다고 한다. 아직 자동화하지는 않았지만 사용 중인 프록시가 API를 제공하므로 자동화가 가능하다고 한다.
- 직접 통제할 대상은 인프라뿐 아니라 애플리케이션 가시성, 데이터 경로, 저장소까지 포함된다. 저자는 집에서는 재미와 학습을 위해, 업무에서는 제대로 일하기 위한 요건으로 이를 실천한다고 한다.
- LLM의 내부 동작을 면접에서 화이트보드로 설명할 만큼 이해하지 못하더라도, 추론 서비스에 계측을 적용해 운영 상태를 파악할 수 있다고 말한다.

## 자세히

글은 아이디어 구현, 코드 작성, 대규모 SaaS 운영 등 용도가 달라도 TUI/GUI/음성 인터페이스를 통해 사용자 데이터를 보내고 응답을 받는 흐름은 같다는 전제에서 출발한다. 예시로 Labubu 신제품 이미지를 ComfyUI로 2D에서 3D CAD로 변환하는 작업과 McRib 영양소 정보를 찾는 작업을 든다. 제공업체는 이 흐름에서 작업 진행 표시를 보여주지만, 저자는 이것이 증거라기보다 주의를 흩뜨리는 화면이라고 본다.

글은 특정 제품이나 구체적인 구성 방법을 다루지 않고 주장과 이유 위주의 짧은 의견 글이다. 캐시 미스 진단 사례도 구체적인 절차나 수치 없이 20초라는 소요 시간만 언급된다.

## 왜 골랐나

AI 에이전트 개발 관점에서, 에이전트와 하네스마다 가상 API 키를 발급하고 호출 로그와 토큰 사용량을 한곳에서 추적하는 방식이 실용적인 운영 아이디어로 맞닿는다.
