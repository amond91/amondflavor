## 한 줄 요약

PHP2Shell(PHP RCE 취약점 2건)을 비롯해 eMudhra, Railway, GitLab, musl, LiteLLM, PingCAP, Linux 커널 비공개 신고 오전송 등 10월 한 주 동안 보안 사고가 집중됐다. 저자는 LLM이 취약점 소식을 실제 공격으로 바꾸는 시간을 주·월 단위에서 시간·분 단위로 줄였다고 보지만, 모든 사고를 AI 탓으로 돌릴 근거는 없고 AI가 보안을 개선할지도 불확실하다고 정리한다.

## 핵심

- PHP2Shell은 CVE-2026-109618·CVE-2026-109619 두 RCE 취약점이다. Calif(OpenAI "Patch the Planet" 참여)와 Wiz(Google Cloud 소속)가 GPT-5.6 Sol/Gemini 4 Argon 같은 LLM으로 찾고 공격 코드를 만들었으며, Wiz는 영향 범위를 인터넷의 70% 이상으로 추산한다. 이 중 CVE-2026-109618은 2024년 PHP Foundation 보안 감사(Sovereign Tech Agency 지원)에서도 발견됐지만, 수정안에 합의하지 못하고 실제 공격 방법도 찾지 못해 남아 있었다.
- 공개 일정이 무너졌다. Hacker News 게시물과 다른 유출로 엠바고가 흔들렸고, PHP Group은 패치 일정을 10월 22일에서 21일로 앞당겼다. PHP Foundation은 Calif의 공격 시연 영상 유출과 Chainguard의 6시간 이른 수정 공개를 문제 삼았다. 약 17시간 동안 여러 문제가 얽혔고, AWS MadPot은 10월 17일부터 시험 시도를 관측했다고 밝혔다.
- AI가 만든 공격 코드의 품질은 따로 봐야 한다. LLM은 잘못된 전제를 깔거나 성공 조건을 바꿀 수 있지만, LiveOverflow의 지적대로 작동하지 않는 코드가 많아도 취약점이 실재한다는 사실은 달라지지 않는다. 작동하는 코드 하나면 충분하고, 이를 가려내려면 실제 보안 전문성이 필요하다.
- 다른 사고 중 AI 사용이 확인된 것은 일부다. LiteLLM 1.107.0(PyPI·Docker)은 .pth 파일 등으로 악성 코드를 실행했고, Wiz는 "LLM 보조 개발" 정황을 지적했다. 반면 eMudhra 중간 인증서 8개 차단(Mozilla, 10월 20일), GitLab의 CVSS 10.0 RCE 2건(정규식 처리), musl regcomp 취약점은 AI 사용 증거가 없다. Railway(환경 변수 접근·복호화)와 PingCAP(FulcrumSec의 10.6TB 탈취 주장)도 AI 사용 여부는 알 수 없다.
- Trend Micro ZDI가 10월 21~22일 밤 Linux 커널의 심각한 취약점 여러 건(CVSS 9.0 이상 포함)을 비공개 목록 대신 공개 메일링 리스트로 잘못 보냈다. 수분 내 실제 공격이 확인된 것은 아니며, LLM 때문에 위험이 커질 것이라는 예상이 근거다.
- 세 가지 대응책에는 모두 한계가 있다. 소스를 비공개로 전환하면 공개 검증의 이점을 잃고 바이너리 역공학이나 과거 공개 버전에는 효과가 없다. 방어자가 먼저 AI로 탐색하는 방식은 비용이 크고 전문성이 필요하며 부유한 AI 기업에 유리하다. 절차 표준화는 비용이 크고 PHP 사례처럼 AWS가 더 이른 시도를 관측한 경우에는 부족하다. 최소 릴리스 경과 시간을 두는 의존성 정책은 활발히 악용되는 취약점의 수정 적용을 늦출 수 있다.
- 결론적으로 최근 며칠은 사고가 비정상적으로 집중됐지만 계속 악화될 "새로운 일상"인지는 단정할 수 없다. 2010년대 자동 분석 도구처럼 일시적 급증 뒤 안정될 수도 있고, 변화가 특정 이해집단이 아닌 공동체 전체에 이익이 되도록 할 책임이 있다고 강조한다.

## 자세히

저자(Drew Silcock, 2026년 10월 23일 글)는 자신이 보안 전문가가 아니라고 밝히고, 기술적 세부는 외부 분석 링크에 맡긴다. 핵심 주장은 패치 공지가 나오는 순간부터 공격 코드가 공개적으로든 비공개로든 유통된다고 가정해야 한다는 것이다. LLM이 코드 변경 내역에서 보안 패치를 찾아 역으로 결함과 공격 경로를 추적할 수 있기 때문이다.

사고마다 AI 관련성이 다르다는 점을 구분한다. GitLab은 HackerOne 버그 바운티로 CVSS 10.0 결함 3건(CVE-2026-97229, CVE-2026-110264, 전월의 CVE-2026-85706)을 모두 신고받았고, 저자는 LLM 때문에 바운티를 폐지하자는 논의와 달리 이 프로그램이 제 역할을 했다고 본다. GitLab은 CVSS 3.1, PHP는 CVSS 4.0을 쓰므로 점수를 직접 비교할 수 없다. LiteLLM은 공격자가 GitHub CLI 자격 증명으로 CI 작업을 실행했고, Claude Code가 때때로 GitHub CLI OAuth 토큰을 응답 본문에 포함해 로그에 남길 수 있다는 경로도 지목됐다.

저자는 온라인 논의가 기존 결함보다 새롭고 위협적인 AI에 쏠리는 경향이 있다고 지적한다. PingCAP 사례처럼 허술한 자격 증명 관리(Jira 티켓에 AWS 비밀 키와 API 키 포함 주장)나 eMudhra의 극단적으로 약한 키처럼 기존 방식의 결함도 중요한 원인이라고 본다. 한편 AI 투자와 기업 이해관계가 논의를 왜곡할 수 있다는 점과, 그렇다고 AI의 실제 영향을 부정할 수는 없다는 점을 함께 언급한다.

## 왜 골랐나

AI 에이전트 개발 관점에서 보면, 코딩 에이전트가 OAuth 토큰을 응답 본문에 남겨 로그로 유출될 수 있다는 LiteLLM 사례와 AI 추론 제공 기업을 겨냥한 Railway 침해 사례가 직접 관련된다. 기술정책 연구 관점에서는 조율된 취약점 공개(엠바고) 체계의 약화, 공공 재원 감사(Sovereign Tech Agency)의 후속 조치 지연, 오픈소스 비공개 전환 논쟁을 다룬 점이 맞닿는다.
