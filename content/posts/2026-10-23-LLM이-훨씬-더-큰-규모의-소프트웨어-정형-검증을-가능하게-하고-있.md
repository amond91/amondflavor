## 한 줄 요약

Anthropic과 Theorem은 Claude로 오픈소스 라이브러리 123개의 퍼징 진입점 239개에 대해 RISC-V 바이너리 수준의 정형 검증(64MB 미만 모든 입력에서 충돌 없음)을 수행했다. 증명 과정에서 수백 개의 버그를 찾아 수정했으며, 증명은 Rocq 검사기가 검증하므로 사람이 증명 전체를 읽을 필요가 없다.

## 핵심

- 기존 퍼즈 테스트를 "이 테스트는 항상 통과한다"는 명세로 자동 변환하고, 64MB 미만의 모든 입력에서 충돌·메모리 안전성 오류·단언문 실패가 없음을 증명했다. 보장은 단일 스레드 정적 RISC-V 바이너리, 고정 메모리 예산, Linux 환경이라는 가정에 한정된다.
- 증명은 총 약 1억 8,000만 줄의 Rocq 코드(일반적인 증명은 약 60만 줄, 대상 바이너리 RISC-V 명령어 수 중앙값 1만 8,000개)이며, 신뢰해야 할 것은 RISC-V·Linux 형식 모델, 증명된 정리의 서술, Rocq 증명 검사기 세 가지뿐이다.
- 증명 시도 과정에서 수백 개의 버그를 발견했다. 약 20MB 입력의 특정 배치에서 생기는 카운터 언더플로, 64MB 입력과 2GB 넘는 메모리가 필요한 경계 밖 읽기, libexpat의 CVE-2026-56132 재발견, 충돌 없는 논리 오류(파일 로드 제한 기능이 항상 적용되지 않음) 등으로, 퍼저가 찾기 어려운 유형이 많았다.
- 충돌 부재 증명은 왕복 일치(LZO 압축·해제), 멱등성, 참조 구현과의 동등성 같은 상위 속성의 증명이 되기도 한다. cpp-httplib 검증에서는 libc++ 레드블랙 트리 재균형이 깊이를 로그 수준으로 제한함을 머신 코드에서 증명해야 했다.
- 그 밖의 실험: Linux 커널 zlib 구현이 RFC 1950 명세를 따름을 x86 바이너리 수준에서 증명(다른 라이브러리 약 6개에도 적용), Rust로 만든 Python 부분집합 인터프리터를 Verus로 검증(무작위 Python 프로그램 170만 개 이상에서 CPython과 99.95% 일치), PDF 리더에서 일주일 만에 통상 1년치 보안 버그 발견.
- 비용 측면에서 증명 생성에는 수억 토큰이 들 수 있다. 소규모 과제 36개에서 Opus 5.5는 Opus 5보다 약 40% 적은 토큰으로 절반을 증명했고, 에이전트 간 증명 복사가 가능한 공유 작업 공간은 토큰 사용량을 17% 줄였다.
- "정형 검증됨"은 "버그 없음"이 아니다. 명세나 머신 의미론이 현실과 다르면 버그가 남을 수 있고, 실제 환경(x86/ARM, glibc 동적 링크)과 주된 증명 대상(musl libc 연결 단일 스레드 정적 RISC-V) 사이에는 차이가 있다. Theorem은 Nix 생태계 전체(glibc, OpenSSL, cURL 포함) 검증을 로드맵으로 제시했다.

## 자세히

핵심 아이디어는 명세 작성의 어려움을 우회하는 것이다. 웹 브라우저나 텍스트 편집기처럼 "올바름"을 정의하기 어려운 소프트웨어도, 개발자가 이미 작성한 퍼즈 테스트를 명세로 삼으면 "이 테스트는 항상 통과한다"는 형태로 자동 변환할 수 있다. Google OSS-Fuzz의 수백 개 프로젝트에 이 방식을 적용했고, C/C++에는 AddressSanitizer가 적용되어 메모리 안전성이 폭넓은 명세로 작동한다.

워크플로는 버그를 발견할 때마다 사람을 기다리지 않고 Claude가 코드를 패치하고 명세를 재생성한 뒤 증명을 이어가는 방식이다. 증명을 끝내지 못하더라도 시도 과정 자체가 고쳐야 할 실제 버그를 찾아낸다. 패치가 필요 없었던 퍼즈 테스트의 완전한 Rocq 증명, RISC-V·OS 의미론, 증명하지 못한 테스트의 명세는 공개하지만, 미패치 버그를 드러낼 수 있는 증명은 공개하지 않는다. Theorem은 다른 오픈소스 프로젝트에 같은 파이프라인을 돌려주는 서비스와 시작용 Claude 스킬도 제공한다.

확장 전략으로는 증명 재사용이 제시된다. 증명은 더 작은 증명의 재귀적 조합이며, C 런타임·ASan 초기화처럼 공통 코드의 증명을 복사·수정했다. Lean의 Mathlib(700명 넘는 기여자, 약 30만 개 정리)과 비교하며, 의존성이 멱법칙을 따르므로 소수의 공유 라이브러리 증명으로 넓은 범위를 검증할 수 있다고 본다. 전망은 정형 검증이 추가 부착 도구가 아니라 개발 과정에 내장된 도구가 되는 것이다. 이를 위해서는 LLM뿐 아니라 언어 설계와 개발 작업 흐름의 혁신도 필요하다고 한다.

## 왜 골랐나

AI 에이전트 개발 관점에서, 에이전트가 증명을 쓰고 Rocq 커널 같은 기계적 검사기가 검증하는 구조와 에이전트 간 공유 작업 공간(토큰 17% 절감)이 참고할 만하다. 기술경영·정책 관점에서는 정형 검증 비용(seL4: 구현 2인년 대 검증 20인년)이 LLM으로 떨어지는 점과, 증명 재사용으로 비용이 분산되는 공유 라이브러리 중심 검증 전략이 눈여겨볼 대목이다.
